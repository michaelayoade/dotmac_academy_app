## Supported transaction and SQL boundary

The source contract requires SQLAlchemy 2.0.51, synchronous PostgreSQL with psycopg, one captured actual Connection and transactional driver connection, and a non-two-phase root. Admission refuses AUTOCOMMIT, two-phase operation, schema translation, and incompatible native control implementations. It preserves the existing genuine Request, Settings-owned policy, canonical authority readers, public Kernel audit and savepoint owners, ReminderLog, outbox, and caller-owned transaction. It introduces no policy defaults, identity writer, shared owner change, migration or standalone commit.

The final SQL decision occurs in permanent dialect-class sentinels for `do_execute`, `do_execute_no_params` and `do_executemany`. They resolve only registered actual Connections and inspect the statement argument passed after cursor transformations. An effective event collection must contain exactly its own sentinel at admission and at dispatch. Earlier or later replacement listeners therefore fail closed for a guarded connection before their bodies execute; unrelated connections retain native dispatch. Short registry locks never cover original methods or callbacks. Permanent inert sentinels hold no ended Request or unit.

Both expression structure and final rendered SQL are checked, including compiled and precompiled statements, TextClause, nested TextualSelect, literal/prefix/suffix fragments, DDL and attached CTEs. The supported rendered grammar is deliberately conservative: one statement, ordinary read SQL, and the exact product-owned DML during its command phase. Transaction and utility commands, comments, separators and concealed extra writes are refused. Bound parameter data is neither treated as SQL nor retained by the guard. The genuine nested textual Settings read remains supported, as do ordinary caller SELECT and native ORM writes after return.

Native savepoint controls have one-use custody tied to the scoped completion frame, exact physical transaction, operation, name, generated clause identity and execution depth. Only final dispatch consumes the permit. A matching name or reused/reentrant clause does not confer permission. Session, SessionTransaction, Connection and physical root/nested completion remain scoped to actual registered objects. Unsupported prepare, prepared completion, detach and transaction-mode changes refuse before the original operation. Actual root rollback aborts the command; genuine caller nested rollback retires only contained receipt epochs and restores the earlier fixed receipt pins. Original V2/V3 exact-effect, participant-completion, idempotence and caller-lifetime protections remain in place.

## Non-destructive authority validation

A bounded dependency barrier observes pending mapped rows in AuthSession, Party, PartyPerson, AcademyAccountProfile, Role, PartyRoleGrant and PlatformSetting using Session collections and mapper state. It does not refresh, lazy load or flush them. Initial pending authority refuses before any refreshing authentication query, preserving the caller's state and history.

At logical caller completion, pending authority defers the fresh read to SQLAlchemy's native flush. After flush, the actual public authority path validates the persisted changes. Benign edits therefore use normal caller ordering, while revoked or invalid authority prevents completion. A physical completion cannot defer a pending dependency. The PREPARED fence uses only the captured Connection and fixed scalar pins; it does not execute through Session. Mutation-generation stamps, dirty authority checks and exact receipt checks remain required at the last physical commit or savepoint release latch, including caught late-listener refusal. No ambient owner flag or synthetic flush loop authorizes completion.

Registration cleanup is exception-safe and identity-checked. Partial installation removes only owned registrations; ending one unit preserves another unit and later wrappers. Root outcome, rather than helper completion, ends guard lifetime. Concurrent separate Sessions have separate custody and receipts; concurrent use of one Session is outside SQLAlchemy's contract.
